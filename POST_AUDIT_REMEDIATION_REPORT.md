## Обновление и сохранность профиля

- **Исходный дефект.** Electrobun 2.0.6 запрашивает разрешение на native quit и затем передаёт работу отдельному helper. Это не вызывает обработчики, подписанные на локальный `app.quit()`. При просмотре собранного Stable дополнительно воспроизвёл отказ проверки feed: сборщик подставлял `true` в ветку, основанную на `NODE_ENV`.
- **Реализация.** `main/updater.ts`, `platform/operation-gate.ts`, `platform/ipc.ts`, `platform/desktop.ts`, `db/core.ts`, `main/agent-mcp.ts`, `main/xn-connect-manager.ts`, `main/window.ts`, `main/authlib/handlers.ts` и `main/remote-servers/index.ts` закрывают вход для новых операций, учитывают активные RPC, запуск relay, Authlib и входящие удалённые команды. После ожидания до 15 с updater даёт до 10 с на остановку MCP и relay. SQLite должна завершить checkpoint WAL без `busy`, после чего соединение закрывается. Синхронное разрешение SDK выдаётся только после очистки. При отказе до native handoff база открывается повторно. Подготовка к перезапуску отменяется через настройки обновления. Dev определяется по метаданным канала.
- **Проверки.** `updater.test.mjs` покрывает ошибку SDK после статуса handoff, отсутствие handoff, повторный вызов, отмену, таймаут, порядок очистки и восстановление. `profile-startup.test.mjs` проверяет реальные checkpoint, закрытие и сохранение записи после повторного открытия. `xn-connect-relay.test.mjs` проверяет реальный TCP relay на loopback.
- **Нативный прогон.** Через обычный RPC упакованного Stable выполнены проверка и подготовка с loopback feed. После удаления файла подготовки в тестовой копии SDK вернул `No valid prepared update is available`. Реальный тестовый stdio-MCP получил EOF и завершился, затем смог подключиться заново. Настройка прочиталась из заново открытой SQLite, версия и хеш исходной установки сохранились. Журнал `.tmp/remediation/update-runtime-release.log`.
- **Ограничения.** Не проверены Windows Scheduled Task, замена установленного каталога, запуск следующей версии и откат после handoff. При таймауте обновление прерывается, уже начатое закрытие стороннего транспорта может завершиться позднее. SDK не даёт общего механизма отмены всех его операций. Рабочий профиль и схема базы сохранены, операции удаления профиля в приложении и updater не добавлялись. Действия нативного деинсталлятора требуют VM.

## RPC и отмена

- **Исходный дефект.** Один час для любого запроса, включая чтение настроек, сборок и аккаунтов.
- **Реализация.** `platform/rpc-timeouts.ts`, `platform/renderer.ts` и `platform/desktop.ts` задают таймаут на отдельный вызов через Electrobun SDK. Чтение SQLite имеет 10 с с учётом пятиисекундного busy timeout. Сетевые запросы получают до 90 с с учётом последовательных HTTP-попыток, файловые сканирования и bootstrap приложения до 2 мин. AI/MCP получают до 5 мин, пользовательские диалоги и длительные импорты или передачи до 15 мин. Текст ошибки содержит канал и срок. Существующая отмена по ID оставлена отдельной от таймаута и доступна для загрузки контента и Share даже при остановке новых операций.
- **Проверки.** `remediation.test.mjs` использует фактический RPC SDK и подтверждает, что потерянный запрос отклоняется, а его поздние и повторные ответы не завершают чужой запрос. `content-download-cancellation.test.mjs` проверяет отмену конкретного скачивания.
- **Ограничения.** Политика задаёт срок ожидания ответа. Нативные и файловые операции без своего механизма отмены могут продолжаться после ошибки ожидания. Дедлайн длительной операции не продлевается по событиям прогресса.

## Один экземпляр и CLI

- **Исходный дефект.** Второй процесс выходил при занятости мьютекса. React мог получить единственную стартовую строку, потерять её при конкуренции и не сообщить результат отправителю.
- **Реализация.** `main/bootstrap.ts` берёт Windows-мьютекс до импорта main. `main/cli.ts` использует локальный named pipe для того же профиля и случайный токен, записанный рядом с конфигурацией расположения. `platform/windows-native.ts` читает аргументы текущего процесса и сохраняет резервное чтение командной строки родительского launcher. Вторичный Bun Worker завершает нативный цикл через `Utils.quit(code)`. `main/window.ts`, preload и компоненты renderer обрабатывают очередь последовательно, с отдельным ID, владельцем запроса и ответом после фактической попытки запуска. Повторное получение того же ID не запускает игру ещё раз. При закрытии окна активный запрос получает ошибку.
- **Проверки.** `remediation.test.mjs` покрывает фокус без команды, очередь до готовности, однократный захват, быстрые запросы, ошибку неизвестной сборки и закрытие окна/приложения.
- **Упакованный прогон.** Bundled Bun и WebView проверили ранний запрос с кириллицей, восстановление свёрнутого окна при повторном запуске без аргументов и две быстрые команды. Существующая сборка с пустой версией получила `No Minecraft version specified` от backend. Несуществующая сборка получила `Build not found` от renderer. Отправители завершились с ожидаемыми кодами, окно осталось одно. Журнал `.tmp/remediation/cli-release.log`.
- **Ограничения.** Windows-мьютекс остаётся Windows-специфичным. Если первичный процесс аварийно завершился уже после запуска игры и до записи ответа в pipe, отправитель получает ошибку доставки и не пытается повторить команду автоматически. Подтверждение успешного старта JVM с полноценной игровой установкой остаётся для VM.

## Артефакты

- **Исходный дефект.** Hutch очищал общий `artifactFolder`.
- **Реализация.** `electrobun.config.ts` и `scripts/electrobun.mjs` используют `release-electrobun/stable`, `release-electrobun/canary` и `release-electrobun/dev`. Обёртка установщика и release workflow берут Stable из его каталога. URL публичного feed и схема манифестов сохранены.
- **Проверка.** `scripts/test-channel-artifacts.mjs` строит Stable, Canary и повторно Stable. После каждой смены канала сверяются файлы, SHA-256 неизменённого канала, ID, версия, ссылки на архив в legacy и v2 и наличие setup. Результаты и предупреждения сохранены в `.tmp/remediation`.

## Прогресс скачивания

- **Исходный дефект.** UI полагался на поле `progress`, даже если у SDK не было счётчиков байтов. Нативная подготовка Electrobun 2.0.6 запускает helper в режиме `--quiet` и получает диагностический хвост stderr без потока счётчиков.
- **Реализация.** `main/updater.ts` рассчитывает процент только при наличии согласованных фактических `bytesDownloaded` и `totalBytes`. `settings-update.tsx` использует неопределённый прогресс, пока нет числа, и отдельное состояние готовности после проверки и подготовки архива.
- **Проверки.** Регрессия не принимает неподтверждённые проценты. Регрессия `scripts/test-native-update.ts` запускает настоящий native helper на loopback. Оба канала отвергли неверный SHA-256, затем подготовили корректные архивы. Источник версии в тесте синтетический. Журналы `native-stage-stable.log` и `native-stage-canary.log`.
- **Ограничение.** Для пути нативной загрузки в текущем SDK доступны состояния, а не байтовый прогресс или отмена самой загрузки. Отмена относится к подготовке перезапуска после завершения скачивания.

## GPU

- **Исходный дефект.** Адаптер `getGPUInfo` возвращал пустой объект, а агент получал пустой список без признака недоступности.
- **Реализация.** `platform/gpu.ts`, `platform/windows-native.ts`, `main/agent-workspace.ts` и тип `AgentHardware` используют read-only CIM `Win32_VideoController` по запросу агента с таймаутом 5 с. Возвращаются имена и, если есть, PCI vendor/device ID. Неизвестный активный адаптер не угадывается. При ошибке или отсутствии данных результат `null`.
- **Проверки.** `remediation.test.mjs` покрывает один и несколько адаптеров, разбор PCI ID, отсутствие данных, отказ CIM и неподдерживаемую ОС. Реальный CIM-запрос вернул один адаптер с PCI ID.

# XNLC/Share: проверка реализации по исходникам Modrinth App

Дата проверки: 1 ноября 2026 года.

Этот документ фиксирует состояние первого прототипа до переделки. Актуальные пользовательские сценарии, запуск и ограничения описаны в [services/share/README.md](../services/share/README.md).

Проверен официальный репозиторий `modrinth/code`, commit `f00f6452984e9dab6965925253ee99bf537706e1`.
Изучены 36 файлов клиентской реализации: Vue UI, Rust API, установка, приглашения, синхронизация и клиентские контракты сервиса.
Это чтение исходников. Работа отдельного серверного приложения Modrinth и его внутренняя схема хранения не проверены.

## Вывод

Текущая реализация XNLC/Share в рабочем дереве — незавершённый прототип. Наличие доменных тестов, HTTP-сервера и успешной сборки не подтверждает выполнение исходного задания целиком.

Главная ошибка реализации — пользовательский сценарий построен вокруг технических операций прототипа: URL сервера, bearer token, ID репозитория, scan, branch и другие команды выведены в одну большую карточку. У Modrinth взаимодействие организовано вокруг аккаунта, приглашения друга, публикации изменений и установки сборки.

## Как устроен Modrinth App

### 1. Аккаунт и привязка

Вкладка Share использует существующую авторизацию Modrinth. Учитываются вход в аккаунт, несовпадение текущего и связанного аккаунтов, недоступность сервиса и карантин сборки. Адрес отдельного Shared Instances API задаётся конфигурацией приложения через `SHARED_INSTANCES_API_BASE_URL`. Токен не вводится в карточке сборки.

Локальная привязка хранит shared instance ID, роль, связанный аккаунт, управляющего пользователя/сервер, статус, применённую и последнюю версии. Привязка и состояние синхронизации записываются транзакционно вместе со ссылкой набора контента.

### 2. Приглашение — основной сценарий

Основное пустое состояние предлагает пригласить друзей. Есть отдельный диалог поиска пользователя и создания ссылки с ограничением срока и количества использований. После появления участников отображается их таблица.

Перед приглашением клиент обеспечивает наличие готовой опубликованной версии. Приглашение не должно вести к сборке с незавершённой первой публикацией. Операции создания ссылки и приглашения защищены блокировкой инстанса.

Получатель проходит разбор приглашения, получение информации, принятие и предпросмотр установки. Клиент проверяет уже установленный инстанс. Создание и установка выполняются через общий механизм установки приложения.

### 3. Snapshot строится на существующей модели контента

`collect_publish_snapshot` вызывает `state::list_content`, затем пакетно проверяет доступность установленных ID версий с обходом устаревшего кэша. Доступные включённые версии попадают в `modrinth_ids`. Файл без доступной версии рассматривается как внешний контент. Для отключённых проектов и версий ведётся отдельное состояние.

Особый случай: удалённая или скрытая версия может оставаться в локальном кэше. Клиент проверяет актуальную доступность; при отсутствии версии сохраняет возможность публикации установленного файла как внешнего. Это отличается от временного сетевого сбоя API.

Дополнительные файлы обходятся отдельно от управляемых каталогов контента. Их публикация требует выбора пользователем.

Источник: [publish.rs, collect_publish_snapshot](https://github.com/modrinth/code/blob/f00f6452984e9dab6965925253ee99bf537706e1/packages/app-lib/src/api/instance/shared/publish.rs#L385).

### 4. Публикация разделена на предпросмотр и отправку

В отдельном модальном окне есть вкладки изменений и дополнительных файлов. Изменения представлены названиями проектов и версиями. Дополнительные файлы выбираются деревом каталогов; изначально они не выбраны. Отображаются размер и квота.

Публикация получает snapshot, хеширует внешние файлы и создаёт версию запросом метаданных: ID контента, имена и типы внешних файлов, Minecraft, загрузчик и его версия. Ответ сервера содержит состояние `ready` и файлы, требующие загрузки. Клиент отправляет запрошенные файлы. При этом нельзя делать вывод о внутреннем алгоритме серверной дедупликации только из клиентского кода.

Передача идёт с ограниченной параллельностью, пакетами и повторными попытками. Прогресс показывает передаваемые байты файлов, запрошенных сервисом, и включается в общий менеджер загрузок.

### 5. Установка и обновления встроены в общий install pipeline

В `packages/app-lib/src/install/shared_instance.rs` строится план изменения контента: добавления, удаления, замены проектов, внешние файлы и конфигурация. Учитываются происхождение контента и существующие локальные записи. Pending-привязка и окончательная привязка различаются; применённая версия фиксируется после успешной установки.

Перед запуском есть проверка доступности общей сборки. Обновление показывается отдельным диалогом с diff и предупреждением о внешних файлах, затем создаётся обычная install job. Окно ожидает события завершения задачи.

Дополнительные файлы в текущем протоколе передаются как дельты. Пропустивший несколько версий клиент собирает их за промежуточные версии, оставляя последнюю загрузку каждого пути. Это не Git-модель коммитов и веток.

## Что неправильно в текущем XNLC/Share

| Участок | Текущее состояние | Необходимая переделка |
| --- | --- | --- |
| Пользовательский интерфейс | Почти весь Share собран в одном большом React-компоненте | Компактная карточка входа, отдельные диалоги публикации, приглашения, установки, обновления; отдельная панель расширенного управления версиями |
| Подключение | Обычному пользователю предлагаются URL сервера и токен | Сначала определить и реализовать реальную авторизацию сервиса Xneon. Настройки собственного сервера вынести из основного сценария |
| Выбор файлов | После scan по умолчанию выбраны в том числе внешние конфиги | Управляемый контент и дополнительные файлы должны иметь разные сценарии выбора; дополнительные файлы требуют явного действия |
| Установка | Предлагается ID репозитория и привязка к уже существующему инстансу | Приглашение → сведения о сборке → предпросмотр → создание нового инстанса через существующий механизм |
| Локальное состояние | Привязка хранится JSON в settings, без связанного пользователя и полноценного состояния задачи | Нормальная доменная модель привязки, миграция SQLite, транзакционная фиксация состояния |
| Учёт установленного контента | Файлы применяются собственным адаптером, обновляются в основном версии игры/загрузчика | Согласовать файлы, БД содержимого, счётчики, события и задания существующего установщика |
| Проверка обновлений | Ручная кнопка внутри карточки | Проверка при открытии/запуске, понятное состояние новой версии и отдельный review |
| Передача | Последовательная работа, ответы и объекты буферизуются, общего resume нет | Ограниченная параллельность, потоковая передача, восстановление задачи и интеграция с Activity Center |
| Версии и совместная разработка | Коммиты, ветки, stash, PR и релизы выведены рядом с базовыми действиями | Сохранить требуемую Git-подобную модель в `@xnlc/share`, но организовать расширенные действия отдельно от сценария «поделиться с другом» |
| Backend | Локальный Node/SQLite/дисковый сервис с предварительно выданными сессиями | Честно считать его прототипом. Исходное задание о production backend, входе, deployment и полном API не выполнено |
| Проверки | Доменные и HTTP-тесты, синтетический каталог, один живой файл Modrinth | Это не полный пользовательский E2E и не доказательство публикации реальной сборки из сотен модов |

## Основа исправления

1. Начать с пользовательских сценариев и постоянной модели состояния: владелец, приглашённый, аккаунт, привязка, applied/latest commit, состояние синхронизации и install job.
2. Встроить Share в существующие инстансы, БД контента, установку и Activity Center.
3. Разделить UI: карточка входа, Share dialog, Publish review, Invite dialog, Install preview, Update review, Members.
4. Оставить manifest и Git-подобные механизмы в независимом `@xnlc/share`. Требования XNLC о SHA-256, Initial Commit, `main`, ветках, PR и merge сохраняются; Modrinth не является готовой реализацией этих требований.
5. Проверить сквозной сценарий двух пользователей с реальными привязками, установкой, перезапуском приложения и обновлением; отдельно измерять передачу на настоящем каталоге.

Изучение Modrinth не означает использование его приватного сервиса для Xneon и не даёт оснований заявлять о готовности нашего backend.

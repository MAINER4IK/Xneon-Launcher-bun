# A01: стоимость безопасной установки

Дата: 15 ноября 2026. Windows x64, Bun **1.4.4**, локальная файловая система. Глобальный `bun` на машине имеет версию 1.3.14, поэтому использован закреплённый `.hutch/toolchain-home/toolchains/bun/1.4.4/windows-x64/bun.exe`.

## Методика

Настоящий `registerBuildHandlers`/Modrinth importer с изолированными DB/provider/scan-портами из `tests/electrobun/modpack-update.test.ts`. HTTP заменён фиксированными in-memory Response, поэтому измеряется локальная оркестрация, файловый I/O и проверка хешей, **не** скорость CDN и **не** реальный parser throughput.

Первый импорт готовит инстанс, измеряется обновление со сменой имён 40 файлов по 64 КиБ (2,5 МиБ) и двумя небольшими overrides. Одинаковые bytes и paths, без очистки OS cache, отдельный процесс/новый временный профиль на каждый из пяти повторов. Сборка не запускалась параллельно измерениям.

Baseline получен до изменения production-кода, после исправления fixture и подтверждённого RED. Финальный замер — после добавления staging/journal/integrity и ограниченного параллелизма чтения. Исходные пользовательские профили не используются.

## Интерпретация

**Ускорение не заявляется.** Медиана операции выросла примерно на 134 мс; CPU также вырос. Прежний путь удалял установленные файлы до загрузки и не делал ни проверяемого сохранения предыдущей версии, ни опубликованного SHA-1 для каждого скачанного файла. Новый путь считает хеши incoming/current, проверяет пути/ссылки, сохраняет write-ahead journal, перемещает старые файлы в backup и проверяет фактический состав до commit. Это дополнительная работа ради сохранности, а не бесплатный структурный рефакторинг.

Профиль одного промежуточного варианта: 745 `lstat`, 128 `stat`, 86 `rename` на этот fixture; повторные path/hash checks существенны. Это счёт вызовов, не доказательство конкретного узкого места ОС. Полного CPU/OS I/O trace не снималось.

Промежуточные попытки:

- Полностью последовательная подготовка: медиана 195,206 мс, диапазон 182,643–204,393 мс, пять повторов.
- Параллельные rename: медиана 625,057 мс, диапазон 607,436–655,024 мс, пять повторов. Этот вариант **не оставлен**. На конкретном Windows окружении он хуже; причина на уровне драйвера/антивируса/очереди Bun не доказана.
- Итог: bounded batches по восемь при подготовке, последовательные rename и один write-ahead журнал на операцию вместо journal rewrite на каждый файл.

RSS здесь — snapshot, а не peak RSS. Timer lag — простой probe, не стандартизованная метрика INP или полноценный монитор event-loop delay. CPU может превышать wall time из-за потоков. Большие реальные паки, длительная сессия, peak RSS и другие платформы не измерены; масштабирование стоимости на них из маленького fixture не выводится.

Дополнительные 134 мс на проверенном маленьком локальном обновлении имеют конкретное объяснение — сохранение и проверка данных. Принимать эту стоимость как production SLA или утверждать отсутствие регрессии всех сценариев нельзя. Контролируемая ремедиация не объявляет performance gate больших паков закрытым.

# Проверка переделанного Share

Проверка выполнена 1 ноября 2026 года.

Проверка ниже описывает предыдущую итерацию с отдельным входом. По уточнению пользователя он удалён: достаточно любого сохранённого аккаунта, кроме offline; активным может оставаться offline. Актуальные тесты охватывают все типы аккаунтов, автоматический challenge/response, защиту от replay и перенос старых прав. Интерфейс перенесён в обычную строку настроек сборки и стандартные диалоги лаунчера.

## Проверка после удаления регистрации

- 11 тестов домена, 8 серверных и 2 файловых теста проходят: всего 21.
- В Electron с отдельным профилем проверено: только offline → `eligible: false`, scan → `ACCOUNT_REQUIRED`.
- Добавлен неактивный Authlib-Injector при активном offline: Share подключился автоматически, без отдельного входа.
- Сборка опубликована через новое окно. Дополнительный конфиг без выбора в manifest не попал.
- Неактивный Authlib-Injector заменён на неактивный Microsoft: доступ сохранился, идентичность владельца не изменилась.
- После удаления всех не-offline аккаунтов сохранённая служебная сессия не позволила выполнить preview: `ACCOUNT_REQUIRED`.
- После возврата аккаунта роль owner сохранилась; в списке участников показывается ник.
- Визуально проверены настройки сборки и окно публикации в тёмной и светлой темах через `applyTheme` с палитрами лаунчера.

Дальнейшие разделы — история проверок предыдущей итерации.

## Автоматические проверки

- `pnpm run build`: renderer typecheck, Vite и Electron TypeScript прошли.
- `pnpm run share:test`: 8 тестов домена и 7 тестов HTTP-сервиса прошли.
- `pnpm run share:test:electron`: 2 теста файлового адаптера прошли.
- Генератор IPC: все каналы имеют preload bridge.

Среди сценариев: сессии и scrypt-пароли, персональные приглашения, предпросмотр без предоставления членства, проверка получателя приглашения, initial commit, дедупликация, конкурентные push, повреждённый объект, сохранение локальных дополнений, явное разрешение конфликта, stash, PR, merge, релиз и restore. Файловые тесты проверяют реальные записи на диске, отказ для symlink/path traversal и восстановление по журналу.

## Реальный Electron и IPC

Использован отдельный профиль в `.tmp`, отдельная SQLite-база и локальный HTTP-сервис. Основной пользовательский профиль не использовался для записи тестовых сборок. UI осмотрен в окне Electron; техническая форма URL/token заменена входом Share и отдельными окнами.

Последовательность проверена через настоящий `window.electronAPI.shareExecute`, без подмены IPC:

1. Создание и вход аккаунта Share.
2. Сканирование исходного инстанса с конфигом `config/pack.json`.
3. Первая публикация без выбора дополнительных файлов: manifest не содержит конфиг, автоматически создан Initial Commit.
4. Повторная публикация с явным выбором конфига.
5. Создание приглашения, вход другого аккаунта, предпросмотр и подтверждение установки.
6. Создан новый инстанс с отдельным каталогом. В SQLite сохранены пользователь, роль viewer, применённый коммит и `up_to_date`.
7. Владелец обновил конфиг до `{"v":2}`. У получателя тот же файл изменён локально; добавлен отдельный `config/local.json`.
8. `checkLaunch` обнаружил `update_available`.
9. Предпросмотр вернул один конфликт; попытка применить без решения завершилась `CONFLICT`.
10. После явного выбора incoming применилось `{"v":2}`, локальный файл остался `{"private":true}`. Привязка стала `up_to_date`.

Фактически отправленное внешнее содержимое последнего обновления: **7 байт**. Это проверка небольшого конфига, а не замер настоящей сборки из сотен модов.

Схема локальной БД: **10**. Дополнительно проверена установка тестового локального JAR: он появился в штатном списке контента и счётчике модов.

## Ограничения проверки

Установка содержимого и работа IPC проверены; сам Minecraft не запускался. Обработка приглашения внутри приложения проверена, системная ассоциация протокола упакованного приложения не проверялась установкой пакета. Сервис не развёрнут в интернете. Его запуск и оставшиеся ограничения описаны в [services/share/README.md](../services/share/README.md).

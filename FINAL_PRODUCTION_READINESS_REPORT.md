# Финальный аудит готовности Xneon Launcher к production

10 ноября 2026 · Windows x64 · рабочий каталог `C:\xnlauncherbun`

## 1. Executive Summary

Из текущего дерева собраны Stable, Canary и однофайловый установщик Windows x64. Распакованные Stable и Canary дошли до рабочего окна с отдельными тестовыми профилями. SQLite сохранила запись из старой базы после миграции v11 → v12. Нативный updater обоих каналов получил манифест с локального feed, отклонил неверную контрольную сумму и подготовил корректное обновление. Для решения о выпуске ещё нужны прогон установки и удаления в гостевой Windows, переключение версии с перезапуском и проверки основных пользовательских сценариев с тестовыми аккаунтами.

## 3. Функциональный аудит

Renderer вызывает `window.electrobunAPI` из `electrobun/preload.ts`. Каналы переходят в реестр `electrobun/platform/ipc.ts` и обработчики main. Ниже отдельно отмечено, где выполнялась логика, а где пройдена только цепочка по исходникам.

| Функция | Выполненная проверка и ограничения |
|---|---|
| Minecraft runtime | Собран отдельный worker. Прослежена цепочка через `minecraft.ts`, `launch-orchestrator.ts` и `minecraft-launch-worker.ts` до `@xnlc/core`. Запуск игры с реальным Java/Minecraft, pre/post-командами и завершение JVM не проверены. |
| Java management | Прослежена цепочка настроек до `java:detect` и нативного выбора файла в `system.ts`. Автоустановка и выбор Java для настоящего запуска не проверены. |
| Microsoft, Ely.by, XnSkins | У каждого провайдера есть отдельный RPC в `auth.ts`, callback/device flow и общий доступ к данным аккаунтов. Запрос списка аккаунтов через WebView RPC вернул пустой тестовый профиль до и после перезапуска. Полный вход и обновление токенов не выполнялись. |
| Modrinth | Прослежены поиск и импорт через `mods.ts`, `builds/index.ts` и `@xnlc/mods`. Тесты содержимого паков и идентификации файлов прошли. Живой импорт пакета не выполнялся. |
| CurseForge, FTB | Прослежены отдельные вызовы поиска и импорта из UI в `mods.ts` и `builds/index.ts`. Импорт с реальным API, зависимостями и отказами CDN не проверен. |
| Сборки и моды | Desktop-тесты выполнили копирование, обновление метаданных без потери незагруженных списков, выключенный контент, отмену загрузки и наблюдение за файлами. Через упакованный WebView RPC дважды прочитаны 20 сборок и содержимое сборки с 450 записями модов, в том числе после перезапуска. |

## 4. Runtime-аудит

- Пакет запустил `bin/launcher.exe`, Bun main и native WebView. Проверены окно с заголовком Xneon Launcher, файл темы старта и маркер инициализации базы. Собраны три worker entrypoint, для relay дополнительно выполнен loopback-тест.
- Smoke через WebView2 DevTools использовал только локальный отладочный порт и вызывал обычный API renderer. Упакованный Stable вернул результаты запросов к main и SQLite, включая событие настройки и её чтение после перезапуска. Повторный запуск Stable с тем же профилем завершился с кодом 0, окно осталось одно. Четыре запуска нормально завершились по закрытию окна. Доставка аргументов уже открытому окну при втором запуске не проверялась.
- Контракты RPC описывают каналы и аргументы. Низкоуровневый ответ `invoke` имеет тип `unknown`, часть методов preload уточняет тип приведением. Общий RPC-таймаут составляет час. Для долгих операций это даёт запас, для обычных вызовов потерянный ответ удерживает ожидание слишком долго.
- В проверенных маршрутах используется Electrobun и Bun. Названия `app`, `getPath`, `before-quit` и Electron в названиях части тестов относятся к совместимости. `getGPUInfo` возвращает пустой объект. Из-за этого агенту недоступна информация об адаптере через этот вызов.
- Ошибка фоновой загрузки модуля remote hosts раньше могла уйти в необработанное отклонение Promise. Теперь она пишется в runtime-лог. Штатный запуск перепроверен, отказ импорта принудительно не воспроизводился.

## 5. Установка и Windows integration

Прочитаны `build/windows-installer.cs`, `scripts/build-windows-installer.ps1`, конфигурация Hutch/Electrobun и реализация AppUserModelID. У внешнего EXE машинный тип PE `0x8664`, файловая версия `1.0.8.0`, версия продукта `1.0.8-pre1`. Вложенный ZIP содержит setup, служебные метаданные и архив приложения. ID метаданных совпал с ID манифестов и AppUserModelID распакованного пакета. Обёртка извлекает только три ожидаемые записи в случайную временную папку и удаляет её в `finally`. Фактическая уборка после отмены и аварийного завершения требует гостевого прогона.

Обёртка проверяет старый тестовый ID `org.xneon.launcher.bun` и записи NSIS в HKCU/HKLM в обоих представлениях реестра. При активной старой установке прямая установка блокируется. На собранном EXE отдельно вызван парсер `UninstallString`. Существующие пути с пробелами и кириллицей распознаны с кавычками и без. Несуществующий путь, строка без закрывающей кавычки и имя с окончанием `.exe.bak` отвергнуты.

Stable и Canary имеют разные пути пакета и feed. Имя продукта, AppUserModelID и пользовательский профиль общие. Фактические имена ярлыков, записи «Установленные приложения», группировка закреплённых окон, обновление поверх установленного пакета и сохранность профиля при удалении требуют запуска native setup. Установщик и деинсталлятор на основной Windows не запускались.

### Изолированный сценарий установки и удаления

1. В гостевой Windows x64 с WebView2 создайте снимок чистой VM. Подключите `C:\xnlauncherbun\.tmp\audit` только для чтения и перенесите `stable-final` и `canary-final` в каталог гостя с пробелами и кириллицей. В госте создайте тестовый профиль и контрольные записи в настройках и SQLite.
2. Запустите однофайловый Stable из гостя. Проверьте выход с кодом 0, путь установки, ярлыки, запуск из меню «Пуск», «Установленные приложения», издателя и значок. Проверьте отсутствие новых `XneonSetup-*` в TEMP после завершения.
3. Из ZIP Canary извлеките setup и скрытую папку `.installer` в одну папку. Установите Canary при уже установленном Stable. Проверьте обе записи удаления, ярлыки, правильные каналы и поведение одновременного запуска с общим профилем. Повторите с запуском Canary первым.
4. Повторно установите Stable поверх Stable. В отдельном снимке повторите сценарий с зарегистрированным прежним NSIS и со старым тестовым ID. Проверьте корректное сообщение о блокировке и отсутствие частичной установки. Для теста достаточно изолированной гостевой регистрации с существующим файлом-деинсталлятором.
5. Удалите один канал, проверьте оставшийся канал, ярлыки и запись второго канала. Удалите второй, сравните контрольные записи SQLite и содержимое профиля с состоянием до удаления. Проверьте отдельно отмену установки и отмену удаления. Восстановите снимок VM.

## 6. Профиль, WAL и SQLite

- Изолированные окружения перенаправляли APPDATA, LOCALAPPDATA, TEMP и профиль WebView2 в рабочий каталог. Приложение открыло `roaming\xneonlauncher\data.db`. Каталог `xneonlauncher-bun` не появился.
- На свежем запуске тестовой базы v11 рабочий файл стал v12, резервный файл сохранил v11, оба сохранили контрольную запись. Desktop-тест держал отдельное соединение с активным WAL и подтвердил, что запись из WAL попала в проверяемый снимок. Это покрывает параллельное чтение во время подготовки снимка и миграцию, но не нагрузочный конкурентный доступ.
- Тест с повреждённым заголовком остановил инициализацию и подтвердил неизменность исходного файла. В штатном завершении есть WAL checkpoint и закрытие соединения. Аварийное выключение во время записи, ручное восстановление из снимка и разрыв обновления во время миграции не проверены.
- Основные управляемые файлы расположены под корнем профиля. Прежний конфиг расположения и явно вынесенные сборки могут использовать другой путь. Служебные файлы установки и updater находятся в LOCALAPPDATA. Проверка каждого внешнего импорта, скриншотов, кэшей и резервных копий через UI не проводилась.

## 7. Производительность

Измерения на одной Windows-машине. Фикстура содержит 20 сборок, у одной 450 записей модов. Замеры не включают загрузку Minecraft и работу с 450 физическими JAR. Скрипты и журналы находятся в `.tmp/audit`. Финальный прогон записан в `runtime-rpc-final.log`, проверка миграции — в `runtime-identity-final.log`, обновления — в `feed-stable-final.log` и `feed-canary-final.log`.

Сборка использовала локально закэшированные Hutch и Bun 1.4.4. Первый вызов с глобальным Hutch не смог скачать Bun. Запуск кэшированного Hutch с `HUTCH_HOME` внутри проекта и `DASH_RELEASE_OFFLINE=1` позволил использовать существующий toolchain. Адрес публичного feed и формат манифестов проекта сохранены.

В двух изолированных копиях пакетов `Resources/version.json` тестово описывал источник версии `1.0.7` с другим хешем и адресом HTTP feed на loopback. Новая версия `1.0.8-pre1` подавалась из реальной локальной сборки соответствующего канала. SDK выбрал v2, а нативная подготовка скачала архив и отклонила неверную контрольную сумму с `ArchiveHashMismatch`. При повторе с правильным манифестом появился `app.prepared-*`, установленный `app` остался прежним. В логах есть состояния checking, available, downloading и download-complete. Процентное продвижение в UI не измерялось. Исходная версия синтетическая. Второй независимой сборки старой версии и полноценной установки обновления с перезапуском в этом прогоне нет.

Для завершения проверки в VM соберите две версии каждого канала с одинаковым loopback URL, установите младшую, затем запустите проверку, скачивание и перезапуск из экрана обновлений. Сравните версию и хеш нового процесса с манифестом и подтвердите сохранность тестовой SQLite. Повторите с отказом на стадии применения и проверьте восстановление предыдущего запуска. Нативный updater Windows использует Планировщик заданий на этой стадии.

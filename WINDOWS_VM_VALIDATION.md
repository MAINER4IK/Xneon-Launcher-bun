# Проверка установки и обновления Xneon Launcher в Windows VM

Выполнять команды только внутри одноразовой Windows x64 VM с WebView2. Даже запуск распакованного `bin\launcher.exe` может создавать ярлыки и запись удаления в HKCU. Для теста нужен отдельный пользователь гостевой системы без рабочих аккаунтов.

## Подготовка

1. Сделать снимок VM. Подключить папку пакета проверки с хоста только для чтения. Скопировать её в `C:\Проверка Xneon Launcher` внутри гостя и отключить общую папку.
2. Убедиться, что в госте нет процесса Xneon Launcher, обоих ключей удаления и каталога прежнего тестового ID. Сохранить исходные значения HKCU/HKLM Uninstall, список ярлыков, TEMP и снимок VM.
3. Запустить setup Stable из подпапки `stable`. Проверить окна подтверждения, завершение с кодом 0, запись «Установленные приложения», ярлыки, запуск из меню «Пуск», имя Xneon Launcher и каталог `%LOCALAPPDATA%\com.xneonlauncher.app\stable\app`. В приложении выставить отличимый язык или тему, создать тестовую сборку. Закрыть лаунчер. Сохранить копию профиля `%APPDATA%\xneonlauncher` с контрольными записями и контрольный файл в этом каталоге.
4. Восстановить чистый снимок. Распаковать ZIP Canary целиком, включая `.installer`, запустить setup из распакованной папки. Повторить проверки с `canary\app` и каналом Beta в настройках. Сохранить снимок с одним установленным Canary.
5. Установить Stable рядом с Canary. Проверить, что записи удаления ссылаются на правильные каналы. Запустить каждый канал по очереди и убедиться, что одновременно с тем же профилем работает только один main. Сверить ярлыки и группировку окон с исходным списком.
6. Переустановить Stable поверх Stable. Проверить один экземпляр записи удаления Stable, состояние ярлыков, контрольную сборку и настройки.
7. Отдельно прогнать распознавание старого NSIS и тестового ID по инструкции ниже. Ожидается явный отказ до распаковки setup.
8. Удалить только Stable через «Установленные приложения». Проверить, что Canary запускается, его ярлык и запись удаления сохранились, а контрольные данные в профиле читаются. Удалить Canary и снова сверить профиль и TEMP.
9. На чистом снимке отменить установку в первом доступном окне и сверить каталоги, ярлыки, ключи и TEMP. На снимке с одним установленным каналом запустить деинсталлятор и отменить в первом доступном окне. Если SDK не предоставляет точки отмены, записать это как ограничение и восстановить снимок.
10. Повторить чистую установку с путями с кириллицей и пробелами. Сохранить журнал, состояние реестра до/после и перечень файлов профиля.

## Фикстуры старых установок

Только на отдельном снимке гостя. Поддельный деинсталлятор служит маркером для распознавания и никогда не запускается.

```powershell
$legacy = 'C:\Проверка Xneon Launcher\NSIS'
New-Item -ItemType Directory -Force -Path $legacy | Out-Null
$uninstaller = Join-Path $legacy 'Uninstall Xneon Launcher.exe'
New-Item -ItemType File -Path $uninstaller | Out-Null
$key = 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall\XneonVmLegacyFixture'
New-Item -Path $key -Force | Out-Null
New-ItemProperty -Path $key -Name DisplayName -Value 'Xneon Launcher' | Out-Null
New-ItemProperty -Path $key -Name UninstallString -Value ('"' + $uninstaller + '" /S') | Out-Null
```

Запустить Stable setup и зафиксировать блокировку. Восстановить снимок до фикстуры и выполнить отдельно следующий сценарий.

```powershell
$old = Join-Path $env:LOCALAPPDATA 'org.xneon.launcher.bun\stable\app\bin'
New-Item -ItemType Directory -Force -Path $old | Out-Null
New-Item -ItemType File -Path (Join-Path $old 'launcher.exe') | Out-Null
```

Запустить Stable setup и зафиксировать блокировку. Снова восстановить снимок.

## Две версии, native updater и rollback

1. Подготовить две изолированные копии текущих исходников и зависимостей в госте. В первой копии установить версию `1.0.7` в `package.json`, во второй оставить `1.0.8-pre1`. В обеих копиях заменить URL только в гостевой `electrobun.config.ts` на `http://127.0.0.1:8789`. Использовать Bun 1.4.4 и Hutch 0.29.0.
2. В каждой копии выполнить `bun install --frozen-lockfile`, `bun run build` и `bun scripts/electrobun.mjs build --env=canary`. Хранить результаты двух версий раздельно. Установить младшую версию нужного канала и создать контрольные данные. Проверить `Resources\version.json` на установленном пакете.
3. В отдельной папке гостя собрать feed из артефактов только новой версии. Запустить `py -m http.server 8789 --bind 127.0.0.1 --directory <папка-feed>`. Открыть обновления в лаунчере и выполнить проверку, загрузку и перезапуск. При необходимости проверить разрешение Планировщика заданий, используя стандартного пользователя VM.
4. Проверить новый процесс, его версию и хеш, сохранность сборки и настроек, открытие SQLite и отсутствие старого процесса. Повторить для другого канала. Отдельно прогнать с работающим тестовым stdio MCP и изолированным relay и зафиксировать их закрытие до handoff.
5. Восстановить снимок с младшей версией. Для отказа загрузки подать v2-манифест с неверным SHA-256 и убедиться, что `app` и профиль не изменились. Для отказа применения сначала успешно подготовить архив, затем перед нажатием перезапуска убрать в госте `<канал>\self-extraction\.electrobun-prepared-update.json`. Проверить явную ошибку, доступность настроек и возможность повторить подготовку.
6. Для проверки отката **после** нативного handoff на новом снимке открыть файл текущего пакета с запретом удаления и переименования. Нажать перезапуск и зафиксировать результат нативного helper, предыдущий хеш и контрольную запись. Убедиться, что отказ возник именно после handoff. Если блокировка не вызвала нужную ветку, записать «не воспроизведено» и повторить под отладчиком в VM. Вернуть VM к чистому снимку.


## Сбор доказательств для второго раунда

Статус всех шагов VM — ожидают выполнения. Убедиться, что у гостя Windows x64, WebView2 и отдельная одноразовая учётная запись. Запускать только локально собранные пакеты с синтетическим профилем. После отключения общей папки убедиться, что гостю недоступны данные хоста.

До установки и после каждого шага выполнить внутри гостя:

```powershell
.\scripts\snapshot-security-vm.ps1 -DisposableVm -Output .\vm-before.json
```

Менять имя файла снимка после каждой операции. Сравнить записи удаления, наличие и целевые пути ярлыков, ACL каталога установки, каналы, хеши и процессы. Для старта открыть окно и проверить отрисовку настроек и дочерний WebView2. При откате зафиксировать, что native helper получил управление, версия и хеш вернулись к прежним, прежнее приложение запускается, а синтетическая контрольная запись читается. При ошибке подготовки или отказе до handoff записать фактическую фазу отдельно.

Для проверки миграции облака создать в синтетической базе запись WebDAV с тестовым паролем, открыть раздел Cloud и убедиться, что запись заменилась на `dpapi:v1:`. Сравнивать только тип записи и результат проверки, избегая вывода её значения. Перезапустить под тем же пользователем и проверить доступ с локальным тестовым сервером WebDAV. После выхода проверить отсутствие строки. Сохранить только журналы статусов и снимки без данных SQLite.
